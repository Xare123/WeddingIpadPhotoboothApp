# Four-photo wedding studio

The local timer candidate, version **0.3.2 / build 5**, defaults to four independent camera originals. Existing five-photo sessions and `wedding-template-v1` recipes remain readable, recoverable and shareable without changing their saved geometry. The app identifier and signing team must stay unchanged when updating an installation containing photos. The final timer installation commit and fresh hosted results must be pinned before owner installation; earlier hosted checks do not verify later files.

The guest flow is capture → review/individual retake → optional photo looks → Make it yours → save keepsake → private QR when ready → Next guests. The camera remains full bleed. Template choices are deliberately small: Photo strip or Four-cut grid, each with **Classic Ivory**, **Sage Botanical** and **Coastal Sea Glass**. Every theme thumbnail is an actual rendered preview using the current four photos. Strip + Classic Ivory + Full photo is the default and needs no adjustment.

## Before capture

A compact camera chip opens independent preparation and following-photo timers. New defaults are 5 seconds first and 3 seconds next, with useful integer stops. Guest edits are session-only, lock at Start and reset to the saved host defaults on Next guests. Hosts can persist both values; valid legacy single-timer preferences migrate to preparation time. Resume and individual retake use preparation time again. Automatic following countdowns wait for the previous durable save and camera readiness, without an extra three-second gap. See [timing and rehearsal](TIMING.md).

## Images and editing

The local Apple Core Image module applies Original, Warm, B&W or Film after capture, with bounded strength. There is no live frame-processor claim. Every look starts from the untouched camera original and writes a separate JPEG; it never repeatedly filters an edited JPEG. A zero-strength/Original selection restores the original identity without re-encoding it. Original, selected derivative and composite are distinct retained assets.

Templates use four unique selected photos exactly once. Tap two photos to swap them; each photo's filter and crop travel with its ID. Full photo keeps every source edge. Newly chosen Fill frame starts at the top, with bounded pan/zoom and a visible warning that edges will be cropped; check every face before saving. Existing crop recipes are unchanged. The same versioned recipe, order, orientation normalization, sRGB pipeline and fixed geometry generate reduced previews and full-resolution JPEGs. A successfully rendered receipt and an actual image load are required before Save. Failed image loading invalidates the receipt and offers a fresh preview retry. View larger renders the actual full-resolution JPEG, with Whole and Fit width inspection modes; it does not enlarge only a UI screenshot.

The V2 strip is **1200×3600 (1:3)**. The social grid is **2400×3000 (portrait 4:5)** or **2400×2400 (square)**. Native source inspection reads oriented dimensions and hashes before the first recipe, chooses portrait when the median oriented width/height ratio is below 0.95, and persists that choice as `gridAspect`. Theme changes and photo swaps cannot change the geometry. Reopening an existing valid V1 or V2 recipe preserves it; V1 grids remain 2400×2100. A mixed set can still need fit bands: preserving full source edges takes priority over silently filling a frame.

Classic Ivory uses an editorial keyline and warm paper, Sage Botanical has original branches and ivory photo mats on sage, and Coastal Sea Glass has original wave contours and ivory mats on sea glass. Decoration stays outside photo windows. The footer reads Gizelle & Rami / November 1, 2026. No vendor assets, user reference screenshots, stickers, printing, face geometry changes or external photo processing are included. See [the local module contract](../apps/ipad/modules/wedding-photo-effects/README.md).

## Preservation and sharing

Camera originals, look derivatives and keepsakes are copied and verified in the app's private documents directory. Versioned journals preserve recipe, order, crop, source lineage and export status independently of SQLite. Staged/superseded files are retained. Changing a selected photo invalidates a mismatched keepsake; confirmation freezes its identity. Repairs preserve completed upload acknowledgements and never overwrite originals.

A new four-photo gallery requires the selected photos, their four corresponding untouched originals and the keepsake. Shared identities are uploaded once; a filtered session can require additional assets. All required uploads and the exact ordered server recipe acknowledgement, including V2 `gridAspect`, must succeed before QR appears. A session-specific bearer link opens the keepsake and individual files; there is no public listing of every guest. Guest-link expiry closes access without deleting originals. The [API contract](API.md) documents legacy compatibility and immutable role/recipe checks. V2 needs its matching backend bundle; the earlier V1 deployment is not sufficient evidence of V2 readiness.

Without Internet the app retains photos and the keepsake, shows No download link yet, and retries sharing later. It does not promise delivery to a departed guest whose contact details were never collected. SMS remains optional, explicit-consent-only and hidden until approved backend capability. Live provider eligibility/configuration and capped real test messages remain coordinator-controlled.

## Photos and host recovery

An optional add-only Photos copy is separate from the private original. A confirmed keepsake can also be exported to Photos. Uncertain results are never retried automatically; authenticated host controls let the owner check Photos, acknowledge an existing copy or explicitly accept duplicate risk. A staged keepsake has its own finish-save action and is excluded from sharing/Photos until verified. Host data relocks and redacts on inactive/background; foreground does not automatically restore the private library. See [saving repair](SAVING_REPAIR.md) and [recipient retention](RECIPIENT_RETENTION.md).
