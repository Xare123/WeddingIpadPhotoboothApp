# WeddingPhotoEffects (local iOS module)

Postcapture editing only. Original JPEG files remain immutable; no camera frame processor or new camera stack is introduced. Expo SDK58 discovers `apps/ipad/modules` automatically. `expo-modules-autolinking resolve --platform apple --json` was run from the iPad app and discovered this module and pod. A new native binary is required; Expo Go and existing binaries lack the module. Hide controls unless `requireOptionalNativeModule('WeddingPhotoEffects')?.capabilityVersion === 1` and recipeVersion matches `wedding-ci-srgb-v1`.

## Contract

- `render(sourceUri, preset, intensity, preview, requestID): Promise<Result>`; preset is `original`, `warm`, `bw`, `film`; intensity finite0…1; preview boolean; requestID fresh UUID per request. Result: `{uri,width,height,recipeVersion,preset,intensity,originalSha256,isOriginal,preview}`.
- `cancel(requestID): void` synchronously marks cancellation under a lock. Checks occur before decode/render/write and after the atomic rename. It cannot interrupt an already executing GPU operation. JS must reject stale results independently and release stale cache URIs.
- `release(uri): Promise<void>` deletes only UUID-named `.jpg` files directly in this engine's own cache, never originals. Repeated release of an absent own-cache file is safe. Release stays asynchronous so it cannot block the JS thread behind the serial render.

The module accepts only file URLs resolving directly inside this app's `Documents/photobooth`, JPEG extension and ImageIO-detected JPEG type. Symlink/path traversal outside that directory, other directories and engine-cache sources are rejected. Callers must resolve the immutable capture record as source every time, and store durable derivatives separately from original files; the module cannot prove provenance if another component copies derivative bytes into the original directory. Never render from a prior derivative. The pure engine intentionally accepts URLs directly to support XCTest; app-container restrictions belong to the module.

Full-resolution `original` or intensity0 returns the exact original URI without re-encoding or metadata changes (`isOriginal:true`). Its reported dimensions are upright display dimensions; original EXIF orientation remains in the source bytes. Preview `original`/zero is visually original-equivalent but must be normalized/downsampled/re-encoded to honor the1440 long-edge cap; it returns `isOriginal:false`. Preview quality is JPEG0.95, not exact source bytes.

## Versioned pipeline and resource limits

`wedding-ci-srgb-v1`: validate single-image JPEG and dimensions; compute SHA256 of unchanged source; decode using embedded source color profile (sRGB fallback), color-manage into sRGB working/output space; apply EXIF orientation1…8 exactly once; translate extent to origin; apply recipe; interpolate original/effect with bounded intensity; crop only to the unchanged original extent (no geometric framing crop); optional Lanczos scale to long edge≤1440; render RGBA8 in sRGB; JPEG0.95 with orientation1. A fresh ImageIO destination receives no source metadata: no GPS, maker notes, comments or camera metadata are copied. ICC/sRGB image profile and structural JPEG properties are retained/generated. Warm uses diagonal RGB gains1.045/1.008/0.955. B&W saturation0/contrast1.035. Film saturation0.86/contrast0.94 plus RGB lift0.018/0.012/0.005. No random grain, vignette, overlays, face changes or additional mirroring. Preview and full-resolution use the same recipe before scale. Any recipe/order/color-space change requires a new recipeVersion.

A shared CIContext disables intermediate caching; all engine render/release operations share one serial queue off the UI thread. Input≤64MiB and≤24million pixels, each axis≤24000. Output cache≤48 files, refuses work above192MiB used and refuses final writes exceeding256MiB. Files are uniquely named; JPEG is finalized in a temporary file then atomically renamed on the same volume. Failed/cancelled jobs remove temporary files. Call release after durable commit or abandoning previews. No cache eviction silently removes a still-displayed result. Large jobs may be rejected instead of exhausting memory; actual device memory/performance still requires validation. At most64 active/queued engine calls are accepted. Recent512 completed request UUIDs cannot be reused; late cancellation for these is ignored. Up to512 pre-registration cancellations are retained so cancel can arrive before the Expo async function starts; excess unknown IDs evict the oldest unknown cancellation without affecting active requests or permanently disabling rendering. On fresh module initialization only engine-owned UUID.jpg/.tmp files are swept; cached URIs from a prior binary/module lifetime must never be persisted as durable references. These are safety bounds, not a GPU interruption guarantee.

## Four-photo templates (new native binary required)

`templateVersion === 'wedding-template-v1'` gates the additional API:

- `renderTemplate(sources: Array<{photoId,uri}>, recipeJSON: string, preview: boolean, requestUUID: UUID): Promise<{uri,width,height,preview,version,recipeJSON,sourceHashes}>`.
- `cancelTemplate(UUID): void`; `releaseTemplate(uri): Promise<void>` (only its separate `Caches/WeddingTemplates` UUID files).

Recipe has exactly `version`, `layout`, `theme`, `photoIds`, `cropsByPhotoId`. Version is `wedding-template-v1`; layout `strip|grid`; theme `classic|botanical|coastal`; photoIds exactly four unique IDs in selected order. Each corresponding crop has exactly `{mode:'fit'|'fill',x:number,y:number,zoom:number}`; x/y range−1…1, zoom1…1.5. Fit requires0/0/1 and preserves every source edge with letterboxing as needed. Fill is explicit opt-in: positive x pans toward the source's right, positive y toward its bottom; zoom increases scale before pan. Preview and final use the identical recipe and full-size composed canvas before final preview downsampling. Returned recipeJSON is canonical sorted-key JSON; sourceHashes maps all four IDs to the actual unchanged JPEG byte SHA256, allowing preview/final source parity checks.

Sources must order-match recipe.photoIds and resolve **exactly** to this app's `Documents/photobooth/{photoId}.jpg`, with IDs matching `[A-Za-z0-9][A-Za-z0-9_-]{0,127}`. Another guest's path cannot be substituted under the selected ID; the caller must additionally authorize selected IDs against the active session. The compositor neither searches for photos nor substitutes/duplicates a missing one. Selected JPEGs can already contain committed filters; no re-filtering occurs. Durable storage must supply the selected logical ID's authorized canonical JPEG before invoking the module; cache sources and alternate filenames are rejected.

Strip is1200×3600: four1080×810 top-left windows at(60,60),(60,894),(60,1728),(60,2562). Grid is2400×2100: windows at(96,96),(1224,96),(96,954),(1224,954). Footer is strictly below photos: built-in Georgia/Helvetica Neue text `Gizelle & Rami` / `NOVEMBER 1, 2026`, with original tiny line/stem/wave vectors. Classic palette is ivory#F6F1E7 / ink#352B25 / accent#BCA68B; botanical sage#EEF1E8 / ink#31483A / accent#8B9B80; coastal#EDF4F2 / ink#274541 / accent#8FB7AE / sand#D4C1A2. These follow the supplied text specification only. Reference screenshots were not accessible/seen, and no vendor art, assets, freeform text, or typography downloads are included.

The source EXIF1…8 is normalized once, embedded color profile honored, and compositing uses the shared serial CoreImage context and sRGB CGContext. Only an explicit fill recipe clips photo content; fit leaves the whole photo visible. Every tile is limited to window pixel bounds during rendering, preventing pathological aspect ratios from allocating huge expanded intermediate images. Whole-canvas preview long edge≤1440, JPEG0.95, orientation1, no source metadata/GPS. Each source≤24MP/64MiB, decoded sequentially with autorelease pools; template canvas≤5.04MP; own-cache limits/cancellation/atomic writes/restart cleanup follow the filter engine's bounds. Originals are read only. Release cache after durable copy; no template URI survives a fresh module lifetime.

`tests/PhotoTemplateEngineTests.swift` adds six actual XCTest methods: all six layout/theme combinations with four distinct edge-marker fixtures/order/source SHA checks; fit vs explicit fill/pan; EXIF6 once; preview/full pixel tolerance+canonical recipe/hash equality; invalid recipe/identity/order/bounds; cancellation/release/restart scope. Existing eight filter tests remain. Include both pure engines and both test files in the native XCTest target, linking CoreText as well as the filter frameworks. **All14 tests remain unrun on Linux.** A Release native compile/runtime test and physical iPad visual/footer/crop review remain gates; simulator source tests do not establish physical optical behavior or template design approval.


## Template v2 refinement (new native binary; local implementation)

The legacy `wedding-template-v1` recipe, geometry, palette and footer rendering remain supported unchanged. The module now advertises `templateVersion: 'wedding-template-v2'` and `supportedTemplateVersions: ['wedding-template-v1','wedding-template-v2']`. Do not relabel or rewrite an existing v1 recipe or confirmed asset.

`inspectTemplateSources(sources: Array<{photoId,uri}>): Promise<{version:'wedding-template-v2',gridAspect:'portrait'|'square',sources:Array<{photoId,width,height,sha256}>}>` validates four unique canonical selected files using the same module path authorization as rendering. The engine inspects single-image JPEG headers with existing 24MP/64MiB limits and computes streamed SHA256 without allocating four decoded bitmaps. Width/height are EXIF-oriented display dimensions; source order and IDs are preserved. It takes the ordinary median of the four width/height ratios (average of the middle two); `<0.95` yields `portrait`, otherwise `square`. Exactly0.95 is square. Inspection does not create or mutate any file. The controller persists the choice and must not rerun classification for theme, order, crop or layout changes. Selected source changes require a fresh inspection; callers still authorize source IDs against their session.

V2 recipes have exactly the v1 keys plus required `gridAspect:'portrait'|'square'`, including Strip recipes. `renderTemplate` keeps its signature, returns the actual recipe version in `result.version`, exact canonical recipe JSON and all four source hashes. V1 forbids `gridAspect`; v2 rejects missing, null or unknown values. The rendering choice is the persisted recipe, not a reclassification on each render. Preview and full use the identical full-size canvas before the preview’s≤1440 long-edge downsample. Default `fit` remains0/0/1 and preserves every photo edge; only explicitly selected `fill` crops.

V2 geometry:

Theme vectors are authored procedural geometry with an even-odd clip that excludes all four photo windows. Sage uses field#DCE5D6, ivory#FAF7EE mats, ink#2D4537, original opposing stems and filled leaves#6D8367 in footer wings and corners. Coastal uses field#DBEBE7, ivory mats, ink#244C49 and visible flowing contour lines#6B9F99 in exterior side fields/footer wings. Art never overlays photo content. Strip footer names use Georgia86px/date Helvetica Neue36px; grid names84px/date32px with baselines inside each reserved footer. No vendor art or typography download is included. A rendered fit photo can still have sidebands when its aspect differs from the deliberately fixed strip window or persisted grid aspect; this preserves the uncropped default.
